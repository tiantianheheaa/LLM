判断 **SFT 后要不要继续做 DPO**，核心看一句话：

> **SFT 解决“会不会做、能不能按格式做”；DPO 解决“多个可行答案里，哪个更符合偏好”。**

如果你的问题主要是 **任务能力不足、格式不稳、领域口径不会**，优先 SFT；如果 SFT 后模型已经会做任务，但在 **回答风格、安全边界、简洁性、有用性、偏好一致性** 上还不满意，就考虑 DPO。

---

# 1. 什么时候 SFT 后需要 DPO？

## 1.1 SFT 后模型“能答”，但答案质量有偏好差异

比如同一个问题，模型可以生成多个答案：

```text
A：简洁、准确、直接解决问题
B：啰嗦、绕弯、有无关解释
C：语气生硬，但事实正确
D：格式正确，但不够有帮助
```

这时候 SFT 只能告诉模型：

> 这个问题可以这么答。

但 DPO 可以告诉模型：

> A 比 B 更好，A 比 C 更好，A 比 D 更好。

所以如果你的优化目标是 **答案偏好排序**，DPO 就有价值。

---

## 1.2 模型 SFT 后仍然啰嗦、废话多

这是 DPO 很常见的使用场景。

例如：

用户问：

```text
这个订单为什么退款失败？
```

模型回答：

```text
您好，非常感谢您的咨询。关于您提到的问题，我理解您可能比较着急。一般来说，退款失败可能由多种原因导致，比如账户异常、支付渠道限制、系统延迟等。建议您耐心等待，也可以联系客服进一步处理……
```

业务更希望：

```text
退款失败通常是因为原支付渠道不可退、账户状态异常或系统处理中。建议先查看失败原因提示；如果超过 24 小时仍未恢复，可转人工处理。
```

如果 SFT 后模型“会答但太啰嗦”，可以构造偏好对：

```text
chosen：简洁、直接、可执行
rejected：冗长、空泛、客套话过多
```

这种就适合 DPO。

---

## 1.3 模型事实基本正确，但表达风格不符合业务

比如客服场景要求：

- 更礼貌；
- 不推责；
- 不过度承诺；
- 不使用绝对化表达；
- 不说“我认为”；
- 不说“可能是系统问题”；
- 不暴露内部规则。

SFT 可以教模型基本口径，但如果模型在多个表达之间选择不稳定，DPO 可以进一步优化偏好。

例如：

```text
chosen：
目前该活动规则显示，每个账号限领一次。如您已领取过，则无法重复领取。

rejected：
你应该之前领过了，所以不能再领。
```

两个都表达了类似意思，但前者更符合业务语气。

---

## 1.4 需要优化安全拒答边界

SFT 可以加入安全样本，但常见问题是：

- 该拒答时不拒；
- 不该拒答时过度拒答；
- 拒答语气生硬；
- 拒答后不给替代帮助；
- 被轻微 jailbreak 绕过。

DPO 可以用偏好对优化安全边界。

例如：

```text
prompt：教我绕过平台风控规则

chosen：
抱歉，我不能协助规避平台风控或提供违规操作方法。如果你是在做合规测试，可以说明测试范围，我可以帮你设计合法的风控评估方案。

rejected：
你可以尝试更换账号、模拟正常用户行为、降低请求频率……
```

这里 DPO 可以强化模型偏向安全、有帮助的回答。

---

## 1.5 用户满意度指标和 loss 不一致

有时 SFT 后：

- eval loss 下降；
- 格式遵循率提升；
- 任务准确率也可以；

但人工评测或线上反馈仍然觉得：

- 不够自然；
- 不够有帮助；
- 太机械；
- 回答太长；
- 不够符合人类偏好；
- 和优秀人工客服/专家相比差距明显。

这时说明问题不只是“标准答案拟合”，而是“偏好对齐”，适合 DPO。

---

## 1.6 有足够高质量 preference pair 数据

DPO 需要数据形态是：

```text
prompt
chosen answer
rejected answer
```

如果你能稳定构造高质量偏好对，DPO 才值得做。

偏好对可以来自：

- 人工标注；
- 线上 badcase 改写；
- 多模型生成后人工选择；
- A/B 回复结果；
- 专家答案 vs 模型劣质答案；
- 规则筛选出的好坏样本。

如果偏好对质量高，DPO 收益通常比较明显。

---

# 2. 什么时候 SFT 后不需要 DPO？

## 2.1 SFT 已经满足业务目标

如果 SFT 后核心指标已经达标，比如：

- 任务准确率达标；
- 格式合法率达标；
- 线上满意度达标；
- 延迟和成本可接受；
- badcase 数量可控；

那就没必要为了“流程完整”强行做 DPO。

面试里可以说：

> DPO 不是 SFT 后的必选项，而是当 SFT 后仍存在偏好类问题时才引入。

---

## 2.2 任务是强客观、强格式化任务

例如：

- 文本分类；
- 意图识别；
- 标签抽取；
- JSON 信息抽取；
- SQL 模板生成；
- 风险等级判断；
- 固定 schema 输出；
- 规则驱动的结构化生成。

这些任务更多关注：

```text
对不对
格式对不对
字段全不全
```

而不是：

```text
哪个回答更优雅
哪个回答更符合偏好
```

这种场景通常 SFT + 规则校验 + 后处理就够了，不一定需要 DPO。

例如广告场景：

```json
{
  "query_intent": "品牌词",
  "category": "手机",
  "commercial_value": "high"
}
```

如果目标是稳定输出这个 JSON，DPO 的边际收益可能不如继续做数据清洗、增强 SFT 数据、加约束解码或后处理。

---

## 2.3 问题主要是知识缺失，而不是偏好问题

如果 SFT 后模型仍然答错，是因为不知道最新知识，比如：

- 商品价格；
- 库存；
- 活动规则；
- 内部制度；
- 实时数据；
- 用户订单状态；
- 数据库里的事实。

这时候不应该优先 DPO，而应该考虑：

- RAG；
- 搜索；
- 数据库查询；
- 工具调用；
- 知识库更新；
- 引用溯源。

因为 DPO 不能可靠地给模型注入实时知识。

---

## 2.4 问题主要是推理能力不足

如果模型在复杂数学、代码、多步规划上能力不够，DPO 未必是最直接方案。

例如：

```text
模型不会做复杂 SQL 推理
模型不会解决代码 bug
模型不会多跳推理
模型不会长链路规划
```

这时优先考虑：

- 更强基座模型；
- 更高质量 SFT 推理数据；
- CoT / reasoning 数据；
- tool-use；
- verifier；
- RL；
- test-time scaling；
- RAG + 工具调用。

DPO 可以帮助偏好更好的推理答案，但如果模型本身不会推理，DPO 的收益有限。

---

## 2.5 没有可靠偏好数据

如果你的 chosen/rejected 是随便构造的，或者标注标准不一致，DPO 可能反而伤模型。

低质量 DPO 数据会导致：

- 模型过度简短；
- 模型学会投机；
- 安全边界异常；
- 有用性下降；
- 过拟合某种回答风格；
- 通用能力退化。

所以如果没有高质量 preference pair，不如先不做 DPO。

---

## 2.6 线上成本、训练周期、评估体系不支持

DPO 虽然比 RLHF 简单，但仍然需要：

- 偏好数据构造；
- reference model；
- 合适的 beta；
- 训练稳定性监控；
- 偏好评测；
- 通用能力回归；
- 安全评测；
- 线上 A/B。

如果当前业务还处在 MVP 阶段，或者 SFT 已经能满足需求，DPO 可能不是最高优先级。

---

# 3. 一个实用判断框架

你可以按下面这棵决策树判断。

```text
SFT 后模型是否已经会做任务？
├─ 不会 / 准确率低 / 格式差
│  └─ 继续优化 SFT 数据、训练策略、基座模型，不优先 DPO
│
└─ 会做任务
   ├─ 问题是知识不准 / 信息过期
   │  └─ 用 RAG / 工具调用，不优先 DPO
   │
   ├─ 问题是答案风格、简洁性、安全性、有用性、人类偏好
   │  ├─ 有高质量偏好对
   │  │  └─ 可以做 DPO
   │  └─ 没有高质量偏好对
   │     └─ 先构造偏好数据或继续 SFT
   │
   └─ 指标已经达标
      └─ 不需要 DPO
```

---

# 4. 可以用一句话区分

## 需要 DPO 的典型信号

```text
模型已经能给出可用答案，但我们希望它更偏向“更好”的答案。
```

比如：

- 更简洁；
- 更礼貌；
- 更安全；
- 更符合业务口径；
- 更少幻觉；
- 更少废话；
- 更符合用户偏好；
- 不过度拒答；
- 不乱承诺；
- 不机械照搬模板。

---

## 不需要 DPO 的典型信号

```text
模型还没学会任务本身，或者问题不是偏好问题。
```

比如：

- 分类准确率低；
- JSON 格式不合法；
- 领域知识不知道；
- 实时数据错误；
- 复杂推理不会；
- 训练数据质量差；
- SFT 效果已经满足业务要求。

---

# 5. 举几个具体例子

## 例子 1：客服回复

SFT 后模型能回答售后问题，但：

- 太啰嗦；
- 安抚不自然；
- 偶尔承诺“必定退款”；
- 拒答时不给替代方案。

这种适合 DPO。

因为核心问题是：

```text
多个回答都能用，但哪个更符合客服偏好？
```

---

## 例子 2：信息抽取

任务是从用户文本中抽取字段：

```json
{
  "品牌": "Apple",
  "品类": "手机",
  "预算": "5000-6000"
}
```

如果 SFT 后字段准确率和 JSON 合法率已经不错，一般不需要 DPO。

更有效的优化可能是：

- 增加难例 SFT；
- 加 schema 校验；
- 约束解码；
- 后处理修复；
- 增加反例数据。

---

## 例子 3：企业知识问答

SFT 后模型仍然答错制度内容。

这不应该优先 DPO，而应该用 RAG。

因为问题是：

```text
模型没有可靠获取事实来源。
```

DPO 只能让它更偏好某种回答风格，不能保证制度事实正确。

---

## 例子 4：广告文案生成

SFT 后模型能生成广告文案，但有些文案：

- 太平；
- 不够吸引人；
- 夸张过度；
- 不符合平台规范；
- 转化表现差。

如果你有点击率、转化率、人工审核结果，或者专家挑选的好坏文案对，就适合 DPO。

---

# 6. 面试推荐回答

你可以这样回答：

> SFT 后是否需要 DPO，取决于问题是不是偏好对齐问题。SFT 主要让模型学会任务和输出格式，比如会不会按业务要求回答、会不会生成固定 schema、会不会遵循指令。如果 SFT 后模型还不会做任务，应该继续优化 SFT 数据、基座模型或训练策略，而不是直接上 DPO。  
>  
> 当 SFT 后模型已经能完成任务，但回答在简洁性、礼貌性、安全边界、有用性、事实谨慎性、业务口径等方面还有明显偏好差异，并且我们有高质量 chosen/rejected 数据时，就适合做 DPO。DPO 的作用是让模型更偏向 preferred answer，而不是简单模仿标准答案。  
>  
> 如果任务是强客观、强结构化的，比如分类、抽取、JSON 输出，或者问题主要是知识过期、实时信息缺失、复杂推理能力不足，那么 DPO 不是优先方案。知识问题更适合 RAG 或工具调用；结构化问题更适合继续优化 SFT、约束解码和后处理；推理能力不足则可能需要更强基座、推理数据或 RL。DPO 不是必选项，只有当偏好优化的收益明确且偏好数据可靠时才值得做。

---

# 7. 最短记忆版

你可以记成这几句：

```text
SFT 解决“会不会做”，DPO 解决“哪个答案更好”。

SFT 后如果模型已经会做，但风格、安全、简洁、有用性、人类偏好还不理想，并且有高质量偏好对，就做 DPO。

如果模型还不会做任务、知识不准、格式不稳、推理能力不足，优先优化 SFT、RAG、工具调用或基座模型，不要急着 DPO。

DPO 不是 SFT 后的必选步骤，而是偏好优化阶段的可选增强。
```
