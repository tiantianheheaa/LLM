下面按面试回答的方式给你梳理。

---

# 1. SFT 的 loss 是什么？

SFT，Supervised Fine-Tuning，本质上还是 **自回归语言模型的 next-token prediction loss**，也就是 token-level cross entropy loss。

给定一条样本：

```text
prompt: 用户问题 / system 指令 / 上下文
answer: 标准回复
```

模型训练目标是让它在看到前文 token 后，预测下一个 token。

形式化地说，假设训练序列是：

```text
x = [prompt tokens, answer tokens]
```

模型对第 `t` 个 token 的预测概率是：

```text
P(x_t | x_<t)
```

那么语言模型的 loss 是：

```text
L = - Σ log P(x_t | x_<t)
```

但在 instruction tuning / chat SFT 中，通常不是对整个序列都算 loss，而是只对 assistant answer 部分算 loss。

也就是：

```text
input:
<system>你是一个助手</system>
<user>解释一下 RoPE</user>
<assistant>RoPE 是一种旋转位置编码...</assistant>
```

训练时：

```text
system 部分：不算 loss
user 部分：不算 loss
assistant 部分：算 loss
```

在代码里通常体现为 label mask：

```python
labels = input_ids.copy()
labels[prompt_position] = -100
```

其中 `-100` 表示该位置不参与 cross entropy 计算。

---

# 2. 为什么 SFT 一般只对 answer 部分计算 loss？

核心原因是：**我们希望模型学习如何回答，而不是学习如何生成用户问题。**

## 2.1 Prompt 是条件，不是目标

SFT 的目标是学习：

```text
P(answer | prompt)
```

而不是学习：

```text
P(prompt + answer)
```

用户输入、system prompt、上下文资料，本质上是条件信息。我们希望模型在这些条件下生成正确 answer。

所以训练目标应该聚焦在 answer token 上。

---

## 2.2 如果对 prompt 也算 loss，会让模型学习“复述用户输入”

如果 prompt 部分也参与 loss，模型会被训练去预测 user 的内容。

例如训练样本：

```text
user: 请你总结这段文本：xxxx
assistant: 总结如下：...
```

如果 user token 也算 loss，模型会学到：

```text
请你总结这段文本：xxxx
```

这类用户输入模式。

但线上推理时，user 输入是外部给定的，不需要模型生成。因此对 user 部分算 loss 对最终回答能力帮助有限，甚至会引入干扰。

---

## 2.3 避免模型角色混乱

Chat 模型中有 system、user、assistant 多种 role。

如果对所有 role 都算 loss，模型可能学到：

```text
user: ...
assistant: ...
user: ...
```

甚至在生成时自己继续生成 user 轮次，导致角色边界混乱。

只对 assistant 部分算 loss，可以明确告诉模型：

> 你只需要学习 assistant 在不同上下文下应该如何回复。

---

## 2.4 更符合指令微调目标

SFT 的目标不是提升模型对训练文本的整体语言建模能力，而是提升：

- 指令遵循；
- 回答质量；
- 输出格式；
- 特定任务能力；
- 对话风格；
- 业务规范遵循。

这些能力都体现在 assistant response 中。

---

## 2.5 提高训练信号效率

如果 prompt 很长、answer 很短，假设对所有 token 都算 loss，那么大量 loss 来自 prompt 部分。

比如：

```text
prompt: 3000 tokens
answer: 300 tokens
```

如果全量算 loss，那么 90% 的训练信号来自 prompt，而不是 answer。

这会稀释真正有价值的回答学习信号。

---

# 3. SFT 能解决什么问题？

SFT 主要解决的是 **行为模式对齐和任务范式学习**，而不是万能地提升模型所有能力。

## 3.1 提升指令遵循能力

让模型更好理解用户要求，比如：

- “请用 JSON 输出”；
- “只输出分类标签”；
- “分三点回答”；
- “不要解释过程，只给结论”；
- “按照给定模板输出”。

这类任务很适合 SFT。

---

## 3.2 学习特定业务任务格式

比如：

```json
{
  "意图": "退款咨询",
  "情绪": "负向",
  "风险等级": "高",
  "建议动作": "转人工"
}
```

如果基础模型经常输出解释性文字，而业务要求固定 schema，那么 SFT 可以显著提升格式稳定性。

---

## 3.3 学习领域表达风格

例如客服、广告算法、医疗助手、法律助手、企业知识助手等场景，都可能有特定表达规范。

SFT 可以让模型学会：

- 回答更专业；
- 语气更符合业务要求；
- 术语使用更稳定；
- 输出结构更统一；
- 拒答方式更符合规范。

---

## 3.4 提升特定任务的准确率

如果任务本身可以通过大量高质量样本示范来学习，SFT 通常有效。

例如：

- 文本分类；
- 信息抽取；
- query 改写；
- 标题生成；
- 摘要生成；
- 多轮客服回复；
- SQL 生成；
- 代码补全；
- 推荐理由生成；
- 广告创意生成。

---

## 3.5 修正基础模型的坏习惯

比如原模型存在：

- 回答太啰嗦；
- 不按格式输出；
- 喜欢补充无关内容；
- 拒答过度；
- 缺少业务口径；
- 输出风格不稳定。

SFT 可以通过高质量示例让模型学习更符合预期的行为。

---

# 4. SFT 不能解决什么问题？

这部分面试很关键，因为很多人会把 SFT 当成万能方案。

---

## 4.1 SFT 不适合注入大量动态知识

如果目标是让模型记住：

- 商品价格；
- 库存状态；
- 实时政策；
- 近期新闻；
- 企业内部经常变化的制度；
- 用户实时画像；
- 数据库内容。

SFT 不是最优解。

原因是：

1. 参数更新成本高；
2. 知识容易过期；
3. 模型可能记不准；
4. 难以追溯来源；
5. 容易产生幻觉。

这类问题更适合 RAG、工具调用、数据库查询。

一句面试回答：

> SFT 更适合教模型“怎么答”，不适合教模型“记住大量经常变化的事实”。

---

## 4.2 SFT 不能可靠解决事实幻觉

SFT 可以一定程度减少幻觉，比如加入拒答样本、不确定性表达样本。

但它不能从根本上保证事实正确。

因为模型本质仍是在生成最可能的 token，而不是实时查证事实。

对于高事实性任务，通常需要：

- RAG；
- 搜索；
- 知识库；
- 工具调用；
- 引用溯源；
- 后处理校验。

---

## 4.3 SFT 不能显著突破基座模型能力上限

如果基座模型本身数学推理、代码能力、复杂规划能力较弱，单靠少量 SFT 通常很难让它质变。

SFT 更像是：

```text
把已有能力引导出来，并对齐到目标任务分布
```

而不是：

```text
从零训练出全新的底层能力
```

如果要显著提升复杂推理能力，可能需要：

- 更强基座模型；
- 大规模高质量推理数据；
- RL；
- 蒸馏；
- verifier；
- tool-use；
- test-time scaling。

---

## 4.4 SFT 不擅长优化主观偏好

比如用户更喜欢：

- 更简洁；
- 更有帮助；
- 更少废话；
- 更安全；
- 更符合人类偏好；
- 两个回答中哪个更好。

这类偏好优化更适合 DPO / RLHF。

SFT 只能模仿一个标准答案，但不能直接学习：

```text
A 比 B 更好
```

而 DPO 可以直接利用 preference pair。

---

## 4.5 SFT 不能保证安全对齐

SFT 可以加入安全拒答样本，但如果安全边界复杂，仅靠 SFT 容易：

- 过度拒答；
- 该拒不拒；
- 被 jailbreak 绕过；
- 安全策略不稳定。

安全对齐通常需要 SFT + DPO/RLHF + 安全评测 + 规则系统共同完成。

---

# 5. SFT 会不会破坏原模型能力？

会，有这个风险。

这就是常说的 **灾难性遗忘，catastrophic forgetting**，或者能力退化。

---

## 5.1 为什么会破坏原能力？

因为 SFT 会继续更新模型参数，让模型分布向训练数据靠拢。

如果 SFT 数据：

- 分布太窄；
- 质量不高；
- 风格单一；
- 任务单一；
- epoch 太多；
- learning rate 太大；
- 数据量太小但训练过久；

模型就可能过拟合到这个垂直场景，导致通用能力下降。

---

## 5.2 可能表现是什么？

常见表现：

1. **通用问答能力下降**
   - 原来能答的常识问题变差。

2. **推理能力下降**
   - 数学、代码、多步推理退化。

3. **表达风格变窄**
   - 无论问什么都用业务模板回答。

4. **拒答策略异常**
   - 该答的不答，或者不该答的乱答。

5. **格式过拟合**
   - 用户没要求 JSON，也强行输出 JSON。

6. **多轮对话能力下降**
   - 上下文跟踪变差。

---

## 5.3 如何缓解？

常见方法：

| 风险 | 缓解方式 |
|---|---|
| 数据分布太窄 | 混入一定比例通用指令数据 |
| 训练过度 | 减少 epoch，early stopping |
| 参数更新过强 | 降低 learning rate |
| 全参破坏大 | 使用 LoRA / QLoRA |
| 过拟合模板 | 增加数据多样性 |
| 不知道是否退化 | 建立通用能力回归评测集 |
| 领域数据质量差 | 强化数据清洗和人工审核 |

面试可以这样说：

> SFT 有可能破坏原模型能力，尤其是数据分布窄、训练轮数多、学习率大时。实际项目中需要做领域任务评测和通用能力回归评测，同时控制训练强度，必要时混入通用指令数据，或者使用 LoRA 降低对基座能力的破坏。

---

# 6. SFT 和 DPO 的区别是什么？

SFT 和 DPO 都是对齐方法，但学习信号不同。

---

## 6.1 SFT 学的是“标准答案”

SFT 数据通常是：

```text
prompt -> chosen answer
```

模型学习的是：

```text
在这个 prompt 下，应该生成这个 answer
```

例如：

```text
用户：解释什么是 RoPE
标准答案：RoPE 是一种旋转位置编码...
```

SFT 的目标是最大化标准答案概率：

```text
maximize log P(answer | prompt)
```

它是 **模仿学习**。

---

## 6.2 DPO 学的是“偏好差异”

DPO，Direct Preference Optimization，数据通常是：

```text
prompt
chosen answer
rejected answer
```

也就是一正一负两个回答。

例如：

```text
prompt: 解释什么是 RoPE

chosen:
RoPE 是一种旋转位置编码，用于让 Transformer 感知 token 位置...

rejected:
RoPE 是一种优化器，可以提升模型训练速度...
```

DPO 不是简单模仿 chosen，而是让模型学会：

```text
chosen 比 rejected 更好
```

目标是提高：

```text
P(chosen | prompt) 相对于 P(rejected | prompt)
```

所以 DPO 是 **偏好优化**。

---

# 7. SFT 和 DPO 的核心对比

| 维度 | SFT | DPO |
|---|---|---|
| 数据形式 | prompt + answer | prompt + chosen + rejected |
| 学习目标 | 模仿标准答案 | 学习偏好排序 |
| 优化方式 | 最大化 answer 概率 | 拉开 chosen 和 rejected 的概率差 |
| 适合阶段 | 建立基础任务能力 | 进一步对齐人类偏好 |
| 解决问题 | 指令遵循、任务格式、领域风格 | 简洁性、安全性、有用性、偏好一致性 |
| 是否需要负样本 | 不需要 | 需要 |
| 对数据要求 | 高质量示范答案 | 高质量偏好对 |
| 风险 | 过拟合、遗忘、学坏格式 | 偏好过优化、reward hacking 类问题 |
| 典型顺序 | 通常先做 | 通常后做 |

---

# 8. 为什么通常先 SFT 再 DPO？

因为 DPO 假设模型已经具备基本回答能力。

如果模型连任务都不会做，直接 DPO 效果通常不好。

合理流程是：

```text
预训练模型
  ↓
SFT：让模型学会怎么完成任务
  ↓
DPO：让模型学会什么回答更受偏好
  ↓
评测 / 部署
```

举个例子：

如果你要训练一个客服模型：

## SFT 阶段

教它：

- 怎么理解用户问题；
- 怎么查询口径；
- 怎么组织回复；
- 怎么按模板输出；
- 哪些问题要转人工。

## DPO 阶段

进一步教它：

- A 回答比 B 更礼貌；
- A 回答比 B 更简洁；
- A 回答比 B 更少幻觉；
- A 回答比 B 更符合安全规范；
- A 回答比 B 更能解决用户问题。

---

# 9. 面试推荐回答版本

如果面试官连续问这些问题，你可以这样回答：

> SFT 的 loss 本质还是自回归语言模型的 cross entropy loss，也就是 next-token prediction。对于一条 instruction 数据，输入是 prompt 加 answer，但训练时通常会 mask 掉 system 和 user 部分，只对 assistant answer 部分计算 loss。这样做是因为 prompt 是条件，answer 才是模型要学习生成的目标；如果对 prompt 也算 loss，会让模型学习预测用户输入，稀释回答部分的训练信号，还可能造成角色混乱。  
>  
> SFT 主要解决的是指令遵循、输出格式、领域表达风格、特定任务范式学习等问题。它适合教模型“应该怎么答”。但它不适合注入大量动态知识，也不能从根本上解决事实幻觉或突破基座模型能力上限。对于实时知识，更适合 RAG 或工具调用；对于偏好优化，更适合 DPO 或 RLHF。  
>  
> SFT 也可能破坏原模型能力，尤其是在数据分布很窄、学习率过大、训练轮数过多时，会造成灾难性遗忘或通用能力退化。所以需要控制训练强度，使用 LoRA、混入通用指令数据，并建立通用能力回归评测。  
>  
> SFT 和 DPO 的区别在于，SFT 学的是 prompt 到标准答案的映射，属于模仿学习；DPO 学的是 chosen answer 相比 rejected answer 更优，属于偏好优化。通常流程是先用 SFT 建立基础任务能力，再用 DPO 对回答风格、安全性、有用性和人类偏好做进一步对齐。

---

# 10. 一句话总结

你可以记住这几句：

```text
SFT 的 loss = answer token 上的 cross entropy loss。

只对 answer 算 loss，是因为 prompt 是条件，answer 才是学习目标。

SFT 适合教模型怎么答，不适合让模型记大量动态知识。

SFT 可能导致灾难性遗忘，需要控制学习率、epoch、数据分布，并做回归评测。

SFT 学标准答案，DPO 学偏好差异。
```
